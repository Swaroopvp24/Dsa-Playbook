# Deep-Dive Technical Reference: Canonical Path Simplification

## Summary
The solution implements a **stack-based state machine** to resolve Unix-style canonical paths. By treating the path as a sequence of tokens delimited by `/`, it leverages a LIFO structure to handle the recursive nature of directory traversal—specifically the "parent directory" (`..`) operator. The algorithm performs a single pass over the string, buffering characters into a `StringBuilder` to materialize token names before applying path logic, ensuring strict adherence to the canonical format (no trailing slashes, no redundant separators, and resolved `.` / `..` operations).

---

## Complexity Analysis

### Time Complexity: $O(N)$
*   **Traversal:** The algorithm performs a single pass over the input string of length $N$. Each character is read exactly once.
*   **Operations:** `processDirectory` is invoked for every `/` encountered. String creation (`directory.toString()`) and stack operations (`push`/`pop`) are amortized $O(K)$, where $K$ is the length of a directory name. Across the whole execution, the sum of all $K$ values is $\le N$.
*   **Result Construction:** `String.join` and `stack.reversed()` operate linearly on the number of elements in the stack, which is bounded by $O(N)$.

### Space Complexity: $O(N)$
*   **Stack:** In the worst case (e.g., `/a/b/c/d/...`), the stack will store nearly $N/2$ tokens.
*   **Buffer:** The `StringBuilder` and local `directoryName` string temporarily store segments of the path, capped at $O(N)$.

## Component Deep Dive

### 1. The Tokenization Strategy
Instead of using `path.split("/")` (which creates multiple transient string objects and fails to handle consecutive slashes elegantly), the manual loop acts as a tokenizer. 
*   **Implicit Handling of `//`:** By checking `!directoryName.isEmpty()` in `processDirectory`, the code inherently ignores empty tokens generated by consecutive slashes (e.g., `///` results in empty strings, which the condition filters out).
*   **Buffer Reset:** `currentDirectory.setLength(0)` provides an efficient way to clear the builder without reallocating the underlying `char[]` buffer, minimizing GC pressure.

### 2. The Stack Logic (`processDirectory`)
The stack serves as the "source of truth" for the current resolved depth.
*   **`..` Logic:** The `stack.pop()` operation safely executes only if the stack is not empty, correctly handling the edge case where `..` is invoked at the root (the root's parent is the root).
*   **`.` Logic:** The identity operator is ignored via `!directoryName.equals(".")`, effectively treating current directory pointers as no-ops.

### 3. Reconstruction
The use of `stack.reversed()` (introduced in newer JDKs) is critical. Because `Deque` (and specifically `ArrayDeque`) represents the path as `[leaf, ..., root]`, reversing it allows for a clean `String.join("/", ...)` to produce the path in `[root, ..., leaf]` order.

## Key Insights

### Performance Optimization: `ArrayDeque` vs `Stack`
Using `ArrayDeque` is a best practice here. `java.util.Stack` is synchronized (thread-safe), which incurs a performance overhead that is unnecessary for local, single-threaded path resolution. `ArrayDeque` is faster and more memory-efficient as it is implemented via a circular array.

### Edge Case Matrix
| Scenario | Behavior | Result |
| :--- | :--- | :--- |
| `//` | `directoryName` becomes empty | Filtered by `!isEmpty()` |
| `/../` | `stack` is empty, `pop` skipped | Returns `/` |
| `/a/./b/` | `.` ignored | Returns `/a/b` |
| `///` | Multiple empty strings | Returns `/` |

### Potential Subtle Pitfalls
*   **Memory Fragmentation:** In high-throughput systems, if the input paths are extremely long, `String.join` and the internal array copying during `stack.reversed()` can trigger significant allocation. For extreme performance scenarios, calculating the total length of the resulting path first and using a pre-allocated `StringBuilder` for the final concatenation would reduce allocations.
*   **Input Constraints:** This implementation assumes the input string contains only valid characters for a filesystem. If the input includes null characters or prohibited filesystem characters (like `\0`), those would be treated as valid directory names, potentially leading to discrepancies with actual OS-level `realpath()` implementations.
